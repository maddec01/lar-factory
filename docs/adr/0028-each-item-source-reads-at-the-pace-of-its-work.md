# Each item source reads at the pace of its work

The board reads each item source on its own, and reads its changed items alone where it can. Every five seconds each GitHub source sends a change check: a REST request for its latest updated issues and PRs, or for its Project, with the last answer's ETag. GitHub answers an unchanged one with a 304, which costs no quota, so the check is free while nothing changes. A changed issue, label, close, sub-issue or PR then reads only the items it touches; a Project's check can't say which item changed, so it reads the Project whole. A source reads its items alone at once when the board, `status.sh` or `slice.sh` names one, and reads whole every five minutes, as a safety read, and on an explicit refresh.

No check sees a PR's checks finish, so an item whose checks run, for at most the 30 minutes past which they show as slow, also reads alone every 15 seconds. A Project or an Azure DevOps team has no check that sees every edit, so there an item reads alone every 15 seconds while it is Active work: its T3 thread, or one of its slices' threads, runs or ran in the last five minutes; it sits in an agent's status while T3 isn't running; it closed in the last five minutes; its checks run; the board shows a change to it that the provider hasn't reported; or an armed start waits on it or for it.

Repository configs and onboarding offers are read on the idle pace and on an explicit refresh only. A rate-limited `gh` or `az` makes no calls until its limit resets, a failed change check waits a minute, and a GitHub quota under a fifth stops the checks and keeps every source at the idle pace. T3's threads and stats refresh from its database alone.

Reading the whole board every 45 seconds spent most calls on work nobody was changing and still ran into GitHub's limits. With the change checks, a repository's issues cost nothing while nobody edits them, and an edit on github.com shows within seconds. Azure DevOps answers no request for free, so an edit made in its web UI to an idle item can take up to five minutes to show, as can an edit to an issue's own content, such as its title, in a Project. We chose this over an operation journal with recovery and per-board notifications. Lar-work's scripts already write through the provider and ask the boards for a read, so a lost request costs one idle interval, not correctness.
