# Refinement publishes only finished work, in the team's terms

Settled in [#688](https://github.com/maddec01/lar-factory/issues/688), built in [#695](https://github.com/maddec01/lar-factory/issues/695).

Refinement stays private until the user approves publishing finished work in the team's language. A concept publishes as one parent ticket with its destination and decision gists, and one child ticket per build, after every decision is settled, its Fog is gone and every brief has passed its current gate. We chose this so published work carries enough context for the team to use it without sharing private execution state or requiring factory setup.

## Consequences

Publication is optional, offered when refinement finishes and available later. A standalone brief also needs a current passing gate. Publishing neither starts a build nor adds unpicked work to the board. Decisions and slices remain private, as do maps, Status, phases and review progress. The private brief remains authoritative even when its published version uses different team wording.

At first publication, the factory detects the team's types and labels or tags. A local Vocabulary mapping inherits optional Repository config defaults beneath explicit local overrides. It maps concept, build and each kind to team terms or nothing, combining applicable labels or tags. Each ticket has at most one effective provider type, and conflicting type mappings require an explicit choice before approval. Unsupported capabilities appear as unavailable, with Refused where access blocks an option. The mapping prompt uses a detected default and a short cost line per option. Publication writes no factory markers, mandatory factory labels, repository tags, private IDs, assignments, priority, iteration, provider State or board changes.

Approval covers an immutable plan with the source revision, destination, mapping, exact content and operations. The factory rechecks it before every outstanding operation and after resume. A changed source, destination, mapping or required write needs a fresh preview and approval, while completed outcomes remain recorded. Build content includes the outcome, change, observable completion checks, confirmed assumptions, decisions and reasons, builder notes, domain-doc notes and related-ticket links.

For a picked ticket, publication appends a clearly marked refined section beneath the author's description. The boundary identifies the content, not the factory. It preserves the original format and content, including Azure HTML. If preservation is uncertain or a body edit is refused, it offers a comment, then a markdown handover when comments cannot be written. Each fallback write needs approval of its concrete operation and content. A handover carries the same content, and attaching its eventual ticket URL preserves the local work identity. Another factory user picks that ordinary ticket into their own work record.

The factory records the exact text last published and its location. Later updates preview a diff and replace only that text after approval. If someone edited it, the user sees both versions and resolves the conflict first. A short update comment accompanies an update only when the ticket is assigned or has a linked PR, and belongs in the approval.

Publication creates the parent, then build tickets in their own repositories, then available native child and blocked-by links. Refused relationships offer approved textual Part of or Depends on links. Each known URL and operation outcome is recorded immediately, with successful, failed and uncertain outcomes reported separately. Successful writes are never rolled back automatically. Before retrying a timeout or partial operation, the factory searches for existing tickets or links and inspects provider evidence, then asks before any retry. Unresolved uncertainty needs the user's resolution. Resume reuses stored outcomes so a lost response cannot cause a duplicate ticket.

A build PR links its published ticket through the provider's closing relationship. Ticketless work keeps a complete PR body and decision gist. Azure closure follows the team's native PR completion setting. Local Done still depends on the recorded PR merging, not on the ticket closing.
