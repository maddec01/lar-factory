# Work records live in one SQLite database

Settled in [#686](https://github.com/maddec01/lar-factory/issues/686) and built in [#693](https://github.com/maddec01/lar-factory/issues/693).

The factory keeps every Work record in one SQLite database, `work-records.db` in the board's data folder, rather than in a folder of JSON and markdown files. We chose SQLite so that one write can change several records in a single transaction. Threads write through the `lar-work` command, and the board will write through the same `work-records` package once it switches. The board app installs a `lar-work` launcher in `~/.local/bin`, which runs the bundled command with the app's own Node, so threads open the database directly from any repository or worktree while the app is closed.

The database opens through `node:sqlite` with T3's settings: WAL journaling, `synchronous = NORMAL`, `checkpoint_fullfsync` on, and a 5 second busy timeout so that a writer waits for another process instead of failing. Each process applies pending migrations in one transaction. Before a migration changes an existing schema, it takes a consistent copy with `VACUUM INTO`, restores that copy through SQLite's backup API if the update fails, and deletes it once the update succeeds. There are no periodic snapshots. Markdown export writes a reading copy of a record's brief, decision or map, which the board never reads back. Retention is a setting on each machine, `retention.json` beside the database, and by default hides a finished or set-aside record after 7 days and keeps it.

Activation is staged. Installing the command alone does not change the installed workflow. [ADR 0004](0004-slices-merge-into-the-build-branch.md) and [ADR 0020](0020-an-items-status-lives-on-the-item.md) still govern the provider-based workflow, while the command adds private slices and local Status as a separate capability. When the board switches to work records, that switch supersedes those two ADRs and the assumption in [ADR 0028](0028-each-item-source-reads-at-the-pace-of-its-work.md) that the provider holds an item's authoritative state.

Amended by [issue #694](https://github.com/maddec01/lar-factory/issues/694): the switch landed. The board now reads and writes work records through the `work-records` package, the same database `lar-work` writes, and lists only recorded work. [ADR 0036](0036-factory-progress-stays-on-the-machine.md) and [ADR 0037](0037-work-has-a-local-identity-and-t3-owns-execution.md) supersede ADR 0020 and the slice sub-issues of ADR 0004.
