# Azure calls go through az devops invoke, and only a work item PATCH through az rest

The board and lar-work's scripts call Azure DevOps through `az devops invoke` and the extension's own commands, as T3 Code does, so every call uses the azure-devops extension's login. invoke has two faults that decide how it is called. It reads `--api-version` as a number by dropping `-preview`, so `7.1-preview.4` fails as `7.1.4`: a preview call passes `7.1-preview`, and az adds the server's latest resource version for it. And of `wit/workitems`' two routes, `${type}` to create and `{id}` to read or update, it always takes the first: a single work item is read through `workitemsbatch` (or `az boards work-item show`, in `status.sh`), and updated through `az rest`, which PATCHes `_apis/wit/workitems/{id}` with the same JSON patch.

We kept that one PATCH, rather than `az boards work-item update`, because its test of `/rev` is what keeps two writes to one work item's tags from overwriting each other, as GitHub's one-label-at-a-time edits never do. `az rest` takes its token from az login's default tenant, which T3 Code avoids, so an organization in another tenant can read but not write until the extension's version parser and route choice are fixed and the PATCH moves back to invoke. A bare `-preview` also means a new preview resource version on the server reaches the board without a change to it.
