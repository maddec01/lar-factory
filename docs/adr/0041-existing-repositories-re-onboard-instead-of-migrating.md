# Existing repositories re-onboard instead of migrating

Settled in [#692](https://github.com/maddec01/lar-factory/issues/692), built in [#694](https://github.com/maddec01/lar-factory/issues/694).

The work-record board starts once with an empty repository list and leaves the old data folder's files untouched. There is no migration. Each repository is onboarded again, and onboarding offers existing factory files as choices to keep or drop. Its first step offers the open tickets that carry a status label or tag, and each kept ticket becomes a work record with that Status. The import matches the ticket's open T3 threads once, by the old first-message rule, and a repeated or resumed run skips tickets already recorded. Status labels and tags stay on the tickets, and removing them is a later opt-in cleanup. We chose this over a migration tool with a preview because the factory had one user and five repositories, with nothing in flight past Shaping.

The ADRs this switch supersedes or amends are [ADR 0004](0004-slices-merge-into-the-build-branch.md), [ADR 0005](0005-read-item-stats-from-t3s-database.md), [ADR 0020](0020-an-items-status-lives-on-the-item.md), [ADR 0021](0021-repository-config-lives-in-the-repository.md), [ADR 0022](0022-onboarding-writes-the-factorys-agent-setup-and-lands-cleanup-through-a-pr.md), [ADR 0023](0023-workflow-labels-have-no-colons-and-the-kind-is-a-label-on-every-provider.md), [ADR 0024](0024-the-board-moves-azure-state-only-when-its-category-changes.md), [ADR 0025](0025-an-azure-work-item-records-its-repository-in-a-repo-tag.md) and [ADR 0028](0028-each-item-source-reads-at-the-pace-of-its-work.md). Each records the change at its end.
